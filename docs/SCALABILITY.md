# 解法与规模扩展边界

## 当前结构

- `src/features/solutions/solutionRegistry.ts` 是解法目录：每个解法登记稳定 ID、展示名称、复杂度、演示限制和帧生成器。
- 算法实现与确定性帧快照由 `src/utils/algorithmUtils.ts` 负责；播放器只消费帧，不在渲染时重新执行算法。
- `useAlgorithmAnimation` 只根据注册 ID 获取快照；输入限制和标签由同一份解法元数据驱动，避免 UI 分支散落。
- `CodePanel` 根据解法 ID 选择独立语言代码与统一 anchor；增加解法时应保持 anchor 跨语言一致，并为步骤映射补测试。
- `VerticalBars` 是题目专属画布，按稳定索引 ID 做 D3 keyed join；动画引擎、时间 token 与通用数据结构留在 `features/animation`。

## 增加一种解法

1. 实现纯算法函数与预计算帧快照，步骤提供稳定 ID、operation、narration、代码 anchor 和完整变量快照。
2. 为解法注册元数据与可演示输入边界；边界只约束交互展示，不改变算法本身的输入契约。
3. 增加对应语言代码/anchor 映射及针对输入、帧有效性、正确结果的单元测试。
4. 更新解法切换 E2E，验证切换重置、代码映射隔离、最终结果和非法输入行为。
5. 只有确实改变可观察结构时才扩展画布；优先以可组合渲染层扩展，避免把解法判断塞入通用播放器。

## 大仓库演进原则

- 按题目/领域与功能边界拆包；依赖方向保持 `UI → feature API → pure algorithm/types`，不允许功能模块互相循环依赖。
- 注册表应保持轻量。题目或解法规模明显增长后，将目录改为按需加载的 feature manifest，并对测试、页面路由和资源采用按需导入；不要预先制造数十万行或一次性 monolith。
- 快照只保留教学关键帧。高密度原始步骤按需生成/分页，画布 DOM 数量必须受可视窗口约束；不能把 LeetCode 的最大输入长度直接等同于同时绘制的 SVG 节点数量。
- 新模块跟随其边界建立测试、lint、类型检查和覆盖率门禁；文档、演示数据和证据与实现一起演进。

## 本题已知边界

双指针为 O(n) 且适合完整交互；暴力枚举为 O(n²)，为避免产生不可读的超长快照，演示限定 n ≤ 9。两者均有独立快照、anchor 与复杂度说明。除这两种有教学意义的经典解法外，不人为添加与标准问题无关的变体。
